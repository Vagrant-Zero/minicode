# minicode 智能编程助手 — 技术方案设计

## 1. 项目概述

### 1.1 背景与目标

在日常开发中，长时间运行的 Agent 任务（如批量代码重构、复杂调试）常面临以下痛点：

| 痛点 | 影响 |
|------|------|
| 上下文丢失 | 长任务中断后无法恢复，需从头开始 |
| API 调用失败 | 网络波动导致任务中断 |
| JSON 解析错误 | Function Calling 参数格式错误导致工具调用失败 |
| Provider 锁定 | 单一 LLM 提供商限制，无法灵活切换 |

**minicode** 是一个基于 ReAct (Reason + Act) 模式的本地 AI 编程助手，旨在解决上述 Agent 鲁棒性问题，提供一个稳定可靠、高度可扩展的本地开发工具。

### 1.2 核心特性

- **ReAct Agent 循环**: 模拟 Claude Code 的核心交互模式
- **多 Provider 支持**: Anthropic / OpenAI / Qwen 统一接入
- **上下文持久化**: SPEC + PLAN 本地文件机制，支持任务恢复
- **鲁棒性设计**: 超时控制、JSON 容错、流式输出处理
- **可扩展架构**: 配置驱动的组件热切换

## 3. 核心功能设计

### 3.1 ReAct Agent 循环

```
用户输入
    │
    ▼
┌─────────────────────────────────────────┐
│ 1. 构建消息                              │
│    messages.append(user_input)          │
└─────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────┐
│ 2. LLM 决策                             │
│    call_api(messages)                   │
│    → 返回文本 + 工具调用                 │
└─────────────────────────────────────────┘
    │
    ├─ 纯文本 → 直接输出
    │
    └─ 工具调用 → 执行工具
              │
              ▼
┌─────────────────────────────────────────┐
│ 3. 执行工具                              │
│    result = run_tool(name, args)        │
│    → 返回工具执行结果                    │
└─────────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────────┐
│ 4. 累积观察                              │
│    messages.append(assistant + tool)    │
│    → 回到步骤 2                         │
└─────────────────────────────────────────┘
    │
    ▼
无工具调用 → 返回最终结果
```

### 3.2 可插拔 Provider 架构

**设计原则**: 改配置不改代码

```python
# 配置驱动
LLM_API_KEY=xxx
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_MODEL=anthropic/claude-opus-4.5

# 运行时自动识别
def initConfig():
    url_lower = API_URL.lower()
    if "openrouter" in url_lower:
        API_PROVIDER = "openrouter"
    elif "dashscope" in url_lower:
        API_PROVIDER = "qwen"
    else:
        API_PROVIDER = "anthropic"
```

**支持的 Provider**:

| Provider | API 格式 | Function Calling |
|----------|----------|------------------|
| Anthropic | Anthropic 格式 | tool_use 数组 |
| OpenAI | OpenAI 格式 | tool_calls 数组 |
| Qwen | OpenAI 兼容 | tool_calls 数组 |

### 3.3 多工具抽象层

```
┌─────────────────────────────────────────┐
│            工具定义 (Schema)             │
├──────────┬──────────┬─────────┬────────┤
│   read   │   write  │   edit  │  glob  │
├──────────┴──────────┴─────────┴────────┤
│            统一执行入口                   │
│        run_tool(name, args)            │
├─────────────────────────────────────────┤
│         工具实现 (Function)             │
│   read()  write()  edit()  glob()      │
└─────────────────────────────────────────┘
```

**内置工具**:

| 工具 | 功能 | 参数 |
|------|------|------|
| `read` | 读取文件 | path, offset?, limit? |
| `write` | 写入文件 | path, content |
| `edit` | 编辑文件 | path, old, new, all? |
| `glob` | 文件搜索 | pat, path? |
| `grep` | 正则搜索 | pat, path? |
| `bash` | 执行命令 | cmd |

### 3.4 MCP 工具扩展

```
┌─────────────────────────────────────────┐
│          MCP 工具扩展层                  │
├──────────┬──────────┬─────────┬────────┤
│ MCP 配置  │ 连接管理  │ 工具转换 │ 统一执行│

         │  外部 MCP Server   │

**MCP 架构**:

| 组件 | 职责 |
|------|------|
| `mcp_servers.json` | MCP 服务器配置 |

| 工具前缀 | `{server_name}_{tool_name}` |

**配置示例**:

  }

```

## 4. 鲁棒性设计

### 4.1 JSON 解析鲁棒性

**问题场景**:
- LLM 输出截断 (达到 max_tokens 限制)
- 输出格式错误 (多余逗号、空值)
- 流式输出时 JSON 被分割

**解决方案**:

| 层级 | 机制 | 作用 |
|------|------|------|
| 源头约束 | strict: true 模式 | 强制模型按 Schema 输出 |
| 截断检测 | finish_reason 检测 | 识别是否被截断 |
| 解析容错 | JSON 解析失败重试 | 携带错误信息让 LLM 重试 |
| 流式分离 | 文本流式 / Tool 整块 | 平衡体验与可靠性 |

```python
# strict 模式配置 (Anthropic)
{
    "name": "read",
    "input_schema": {
        "type": "object",
        "properties": {...},
        "required": [...],
        "strict": true  # 强制输出符合 Schema
    }
}
```

### 4.2 命令执行超时控制

**问题**: Bash 命令可能死循环或执行过长

**解决方案**:

```python
def bash(args):
    proc = subprocess.Popen(args["cmd"], shell=True, ...)
    try:
        proc.wait(timeout=30)  # 30 秒超时
    except subprocess.TimeoutExpired:
        proc.kill()
        return "(timed out after 30s)"
```

### 4.3 流式输出与 JSON 解析冲突

**问题**: 流式输出时，JSON 可能被分割成多个 chunk

**解决方案**: 分离处理

| 输出类型 | 方式 | 原因 |
|----------|------|------|
| 最终回答 | 流式输出 | 提升用户体验 |
| Tool Call 参数 | 整块返回 | 确保 JSON 完整性 |

## 5. 上下文管理机制

### 5.1 SPEC + PLAN 本地文件

```
项目目录/
├── .spec.md          # 需求规格
├── .plan.md          # 任务计划
├── .minicode/       # (可选) 状态缓存
└── src/              # 项目代码
```

**SPEC 模板**:
```markdown
## 需求规格

### 目标
[用户描述的任务目标]

### 约束
- 约束条件 1
- 约束条件 2

### 验收标准
- 标准 1
- 标准 2
```

**PLAN 模板**:
```markdown
## 任务计划

### 状态: 进行中

### 步骤
- [x] 1. 阶段 1 描述
- [x] 2. 阶段 2 描述
- [ ] 3. 阶段 3 描述

### 当前阶段
3. [阶段描述]

### 关键节点
- 阶段 1: [完成情况摘要]
- 阶段 2: [完成情况摘要]
```

### 5.2 上下文压缩机制

**问题**: messages 累积会导致上下文膨胀

**解决方案**: 定期压缩

```
触发条件:
- 每隔 N 步 (如 5 步)
- Token 超过阈值 (如 4000 tokens)
- 任务切换时
```

**压缩流程**:

```
Step 1: 检测需要压缩
        ↓
Step 2: LLM 生成摘要
        "阶段1: 分析完成，发现3个问题
         阶段2: 提取UserService完成
         活跃文件: auth.py, user.py"
        ↓
Step 3: 替换 messages
        旧: 100 条原始消息 (8000 tokens)
        新: 2 条压缩消息 (300 tokens)
        ↓
Step 4: 更新 PLAN
        持久化检查点到磁盘
```

**压缩效果**:

| 阶段 | 原始 messages | 压缩后 |
|------|---------------|--------|
| 初始 | 10 条, 500 tokens | 10 条, 500 tokens |
| 50 轮 | 110 条, 8000 tokens | 2 条, 300 tokens |

### 5.3 任务恢复流程

```
用户: "继续上次任务"
    │
    ▼
1. 读取 .spec.md (需求)
2. 读取 .plan.md (进度)
3. 构建压缩后的 messages
4. 继续 ReAct 循环
```

## 7. 效果与价值

### 7.1 解决的问题

| 问题 | 解决方案 | 效果 |
|------|----------|------|
| 上下文丢失 | SPEC + PLAN 持久化 | 支持任务中断恢复 |
| 上下文膨胀 | 压缩机制 | 常数级上下文大小 |
| API 失败 | 多 Provider 切换 | 灵活应对服务问题 |
| JSON 错误 | strict 模式 + 容错 | 减少工具调用失败 |
| 命令超时 | 30 秒超时控制 | 避免死循环阻塞 |

### 7.2 技术亮点

1. **可插拔架构**: 配置驱动的 Provider 热切换
2. **上下文管理**: 持久化 + 压缩的双层机制
3. **鲁棒性设计**: 从源头约束到容错处理的全链路方案
4. **本地优先**: 无需外部服务，隐私安全
